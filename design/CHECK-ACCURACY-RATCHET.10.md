# Check-accuracy ratchet — historical rationale

`test/go/langspec/check_accuracy_test.go` runs three ratchets over the whole
`lang/spec/` corpus (checker false-positives, unflagged `ERROR:` rows, and
type-soundness violations) plus an informational Any-frontier precision metric.
Each pin used to carry its entire change-history as a single append-only
trailing `//` comment — one physical line grew past 20 KB, so every routine
pin bump (which happens on nearly every checker or spec-corpus change) produced
an unmergeable single-line conflict.

The counts now live in the test as small, localized constants — in particular
the unflagged count is a **per-file `unflaggedPins` map**, so adding rows to one
spec file edits only that file's line. This document is where the *why* moved:
the archaeology below explains how each count reached its current value. It is
append-only reference; the live numbers are authoritative in the test.

See also `design/legacy/checker-accuracy-review.10.ignore` (§5, the ratchet's design).

## Unflagged error rows (now the per-file `unflaggedPins` map)

`ERROR:` rows the checker stays silent on — dominated by runtime-only /
value-dependent errors that are the runtime's job, not statically flaggable.
This was a single global pin; the aggregate evolution is recorded here, and the
count is now tracked per spec file in `unflaggedPins`.

2026-08-26, NUR103 record-field fix — two NEW entries, `edge-quote-1.tsv: 1`
and `edge-quote-3.tsv: 1`, and one row added elsewhere. Both files carry the
same shape: a WORD element pulled out of a quoted list bare (`quote [add 1 2]

check mode `get` yields a Word-TYPED CARRIER, and the step loop classified on

runtime-only, like the rest of this map. The same commit resolves an inline

(`ResolveSigRecordFields`), which is what produced the bad carrier in the
